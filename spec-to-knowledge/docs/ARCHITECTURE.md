# 아키텍처

## 1. 처리 파이프라인

```
source.pdf
  │
  ├─(1) 밴드 스캔(pypdfium2): 모든 페이지의 상·하단 영역 텍스트 → 반복 패턴 = 머리글/바닥글
  │
  ├─(2) 페이지 분석(pdfplumber, 페이지마다 독립 실행·실패 격리) ─────────────── raw/pNNNN.json
  │      글자 → 단어(글꼴·크기·굵기) → 줄 조각(넓은 간격에서 분리: 2단·무괘선 표 대비)
  │      ├ 머리글/바닥글·쪽번호 제거, 목차 페이지 판정, 스캔 페이지 판정(텍스트 없음 + 큰 이미지)
  │      ├ 괘선 표: 셀 좌표로 행·열 경계를 계산해 rowspan/colspan, 굵은 행 = 머리글
  │      ├ 캡션: "Table N —"/"Figure N —" (구분자·굵기·가운데 정렬로 본문 언급과 구별)
  │      ├ 표 캡션 ↔ 표 연결(위/아래/자동), 표 없는 캡션은 텍스트 정렬로 무괘선 표 재구성
  │      ├ 도형(선·사각형·곡선·이미지) 군집화(스윕 + union-find) → 라벨 텍스트 흡수 → 그림 캡션 연결
  │      │   · 캡션 있는 그림은 내부의 ‘약한 표’(캡션 없는 격자)를 흡수, 캡션 없는 군집은 크기 기준으로 보존/폐기
  │      │   · 도형이 없는 캡션은 캡션 주변 영역을 그림으로 추정(경고)
  │      ├ 2단 감지(General): 가로 위치별 교차 줄 수로 거터 탐색 → 밴드별 왼쪽→오른쪽 읽기 순서
  │      ├ 남은 줄 → 블록: 간격·글자 크기·들여쓰기·글머리/열거/NOTE 패턴, 제목 후보(번호/부록/큰 글씨)
  │      └ 그림(PDF 좌표 영역을 200 DPI로 렌더링)·표 원본 이미지 저장
  │
  ├─(3) OCR(스캔 페이지만, Provider) → raw 페이지에 OCR 텍스트 저장
  │
  ├─(4) 문서 조립(assemble): raw 페이지 전체 → Canonical
  │      ├ 본문 글자 크기(문단 기준 최빈값) → 제목 확정: 강조(굵게/크게) + 번호 순서 검사
  │      ├ 표지·제목 블록 처리, 표 ID 중복 정리, 연속 표 병합((Cont'd) 또는 다음 페이지 첫 요소), 페이지 넘김 문단 연결
  │      ├ 메타데이터(제목·문서번호·리비전) 추출
  │      └ overlay(사용자 수정·이슈 상태·메타데이터) 재적용, 같은 이미지의 AI 설명 승계
  │
  ├─(5) Vision: 유형 분류(규칙/LLM) → 프롬프트 → Provider(동시 호출, 캐시) → JSON 파싱 → 원문 대조
  │
  ├─(6) 검증: 원문(텍스트 레이어) ↔ 생성 Markdown(블록별 렌더링 → 평문) 페이지 단위 대조
  │           + 표 구조 + 번호 + 그림·OCR 상태 + 내보내기 링크·Frontmatter
  │
  └─(7) 내보내기: 절 단위 분할 → 공통 Frontmatter → 블록 렌더링 → 목차·그림/표 목록 → assets 복사
                 → source_map.json → mkdocs.yml(또는 Home/_Sidebar) → _meta → ZIP
```

## 3. 핵심 설계 결정

1. **Canonical JSON을 기준 데이터로 둔다.** Markdown은 언제든 다시 생성할 수 있는 결과물입니다. 사용자 수정은 Markdown 파일을 직접 고치는 대신 블록·표·그림 단위 `md_override`로 저장하므로, 다시 내보내도 공통 규칙(Frontmatter, 파일 분할, 링크)이 유지되고 수정 내용도 다시 검증됩니다.
2. **raw 페이지와 overlay를 분리한다.** 페이지 재처리는 raw 파일 하나만 바꾸고 전체를 다시 조립합니다. 블록 ID는 `p<페이지>-b<순번>`처럼 위치 기반이라 같은 위치의 수정이 다시 적용되고, 대상이 사라지면 `edit_orphaned` 이슈에 수정 내용을 남깁니다.
3. **제목은 문서 단위로 확정한다.** 페이지 분석은 후보만 표시하고, 전체 본문 글자 크기와 번호 순서(직전 번호의 자식·형제·상위 형제인지)를 보고 확정합니다. 본문 속 "2 Normative…" 같은 목록이나 "1.2 V" 같은 수치를 제목으로 잘못 잡는 일을 줄입니다.
4. **검증은 생성기와 같은 렌더러로 한다.** 검증기는 블록마다 exporter와 같은 Markdown을 만들어 평문으로 되돌린 뒤 원문과 비교합니다. 이스케이프나 표 변환에서 생긴 손실도 잡을 수 있습니다. AI 설명은 비교 대상에서 빼서, 모델이 쓴 수치가 본문 누락을 가리지 못하게 합니다.
5. **표 구조를 잃지 않는다.** 병합 셀이나 다중 머리글이 있으면 HTML 표로 내보냅니다(MkDocs·GitLab·GitHub 모두 렌더링). 단순 표는 GFM으로 내보냅니다. 강제 GFM 모드에서는 병합 값을 반복하고 머리글을 `상위 / 하위`로 평탄화합니다.
6. **인프라를 최소화한다.** DB, 큐, 프런트엔드 빌드 없이 파일 저장소와 스레드 풀만 씁니다. 폐쇄망 설치는 휠 번들 하나로 끝납니다. 단점은 단일 프로세스 운영이라는 점입니다(README 11.4 참고).

## 4. 동시성과 일관성

- 문서마다 실행 중인 작업은 하나만 허용합니다(`JobManager.active_by_doc`). 작업 중 편집 요청은 409로 거부합니다.
- 파일 쓰기는 모두 원자적입니다(임시 파일 → fsync → rename). 문서별 RLock으로 canonical과 overlay를 갱신합니다.
- 작업 상태는 문서 레코드를 갱신한 **다음에** 완료로 공개합니다. 그래서 작업을 폴링하는 쪽이 이전 상태를 읽지 않습니다.
- 취소는 페이지·그림 단위로 확인하며, 취소되면 canonical을 저장하지 않습니다(이전 결과 유지).
- pypdfium2(PDFium)는 스레드에 안전하지 않아 전역 잠금으로 보호합니다. pdfplumber 문서 객체는 작업마다 따로 엽니다.

## 5. 확장 지점

| 바꾸고 싶은 것 | 위치 |
|---|---|
| 새 문서 유형 규칙 | 프로필(코드 수정 불필요): 제목·캡션·NOTE·목록 패턴, 머리글 패턴, 표·그림 기준 |
| 새 그림 유형 | 프로필의 이미지 유형 규칙(정규식, 지침, 출력 항목) |
| 새 모델 API | 대부분 Custom HTTP로 해결됩니다. 서명 인증처럼 특수한 경우에만 `Provider` 하위 클래스를 만들어 `providers/store.make_provider`에 등록합니다. |
| 새 검증 규칙 | `validator/checks.py`에 함수를 추가하고 `validate()`에 연결합니다. |
| 새 출력 레이아웃 | `exporter/package.py`의 `DocumentExporter.page_path/link`와 `build_kb` |
